Experience

Backend Engineer Intern
Salhakar (Legal Tech Startup) • 3 Months • Summer 2024 • Paid Internship

Joined Salhakar to solve a foundational problem: Indian lawyers spend hours manually searching through scattered court judgments and legislation. The vision was to build a unified legal search engine—but the existing infrastructure couldn't scale. I was tasked with architecting a system that could index and search 16 million documents with sub-second latency.

16M Court Judgments
50K Docs Curated
100GB ES Indices
<200ms Query Latency

The Data Challenge: From Chaos to Structure

The Problem: 16 million High Court and Supreme Court judgments scattered across multiple sources in inconsistent JSON formats. Additionally, I personally curated ~50,000 legal documents—30,000 Indian Acts (State + Central legislation) and 20,000 High Court/Supreme Court judgments—from raw, unstructured sources. Missing metadata, duplicate entries, and incomplete records everywhere.

The Solution: Built a comprehensive ETL pipeline that unified this chaos into a clean PostgreSQL schema. For the 50K manually curated documents, I developed data validation scripts, standardized metadata extraction, and quality checks to ensure consistency. Implemented intelligent deduplication using case numbers, judgment dates, and fuzzy title matching across the entire corpus. Created checkpoint tracking for fault-tolerant batch processing—when processing millions of records, failures are inevitable. The pipeline needed to recover gracefully.

The Impact: Transformed 16M+ scattered documents plus 50K hand-curated legal texts into a queryable, deduplicated database. Established a single source of truth for all legal content, enabling downstream AI and search systems to actually work reliably.

Distributed Search Infrastructure: Making 16M Documents Searchable

The Problem: PostgreSQL full-text search couldn't handle 16M documents with acceptable latency. Traditional LIKE queries took 10+ seconds. Users expect Google-speed results—hundreds of milliseconds, not seconds.

The Architecture: Designed and deployed a 4-node Elasticsearch cluster on Digital Ocean. Implemented custom indexing strategies with field-specific analyzers for legal terminology. Built incremental sync pipelines that kept Elasticsearch indices in sync with PostgreSQL as new judgments were added. Tuned sharding and replica configurations to balance query performance with cluster resilience.

The Challenge: Legal documents aren't just text—they're structured hierarchies. Judgments reference other judgments. Acts have sections, subsections, provisos. The index needed to preserve this structure while remaining fast. Implemented nested document mapping with proper parent-child relationships.

The Result: Sub-200ms query latency across 16M documents. Full Boolean search, proximity queries, faceted filtering by court/year/judge. The system could handle complex legal queries like "Section 498A IPC within matrimonial disputes in Karnataka High Court between 2015-2020" and return results instantly.

API Design: Serving Mobile & Web at Scale

Async-First Architecture: Built FastAPI endpoints with full async/await throughout the stack. When you're serving both web frontend and mobile apps, blocking I/O is not an option. Every database query, every Elasticsearch request, every external API call—fully asynchronous.

Production Deployment: Single-handedly deployed the entire backend infrastructure on Digital Ocean. Used App Platform for the FastAPI application with auto-scaling and zero-downtime deployments. Configured Spaces for object storage—16 million PDFs don't fit on local disk. Set up the 4-node Elasticsearch cluster managing 100GB+ of indices across distributed shards. Handled everything from DNS configuration to SSL certificates to load balancer setup.

The Infrastructure Stack: PostgreSQL on managed databases for transactional data. Elasticsearch cluster for search indices (100GB+ across 4 nodes with proper shard distribution). Digital Ocean Spaces CDN for serving PDFs globally. Redis for caching frequently-accessed data. Implemented proper connection pooling, health check endpoints, structured logging with log aggregation, and metrics collection for production monitoring.

Developer Experience: Created clean REST APIs with automatic OpenAPI documentation. The mobile team could test endpoints directly from the docs. Web team got predictable response structures. Everyone stayed productive while I maintained 99.9% uptime.

AI Pipeline: From Scanned PDFs to Structured Knowledge

The OCR Challenge: Many court judgments are scanned PDFs—images, not text. Traditional OCR breaks on legal documents with complex formatting, tables, multi-column layouts, and mixed English-Hindi text.

GPU-Accelerated Processing: Integrated MinerU and Docling for GPU-accelerated PDF to Markdown conversion. These aren't simple OCR tools—they're document understanding models that preserve structure. Tables stay tables. Hierarchies are maintained. Citations remain intact.

Citation Extraction: Built a citation extraction pipeline that identified references between judgments. This enabled knowledge graph construction—mapping how legal precedents flow through case law. A judgment from 1975 might be cited in 500 later cases. Those relationships are goldmines for legal research.

Hybrid Search: Implemented BM25 (keyword) + semantic (AI embeddings) hybrid search. Lawyers search in different ways—sometimes they know exact legal terms (BM25 handles this), sometimes they describe situations in natural language (semantic search handles this). The system needed to excel at both.

What I Learned

This internship taught me what it means to own a system end-to-end. I didn't just write code—I deployed it, monitored it, debugged it at 2 AM, and kept it running in production. From Docker containers on App Platform to 100GB Elasticsearch indices across 4 nodes to CDN configuration for 16M PDFs—every piece was my responsibility.

I learned that distributed systems are about tradeoffs. Fast writes vs. fast reads. Consistency vs. availability. Storage costs vs. query performance. Vertical scaling (bigger machines) vs. horizontal scaling (more machines). Every architectural decision had real consequences measured in dollars and milliseconds.

I learned that "16 million documents" isn't just a number—it's a scale where naive solutions break. Where you need to think about memory pressure, disk I/O patterns, network saturation, shard distribution, and garbage collection pauses. Where monitoring and observability aren't optional—they're survival.

Most importantly, I learned to build systems that outlast my time there. The infrastructure needed to be maintainable, documented, and operable by others. Good code isn't just correct—it's comprehensible. Good architecture isn't just fast—it's debuggable.
